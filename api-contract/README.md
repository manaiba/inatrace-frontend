# Backend OpenAPI contract and Angular client

The pinned `openapi.json` and `manifest.json` were produced by
`manaiba/inatrace-backend` at the revision in the manifest. A SHA-256 match
proves the files are internally consistent; independently verify the source
repository, workflow run and full revision before trusting a new artifact.

Use Node 14 and Java 17:

```bash
npm run check:api
npm run test:api-generator
npm run audit:api-models
```

`check:api` validates the producer manifest and spec hash, generates in a
temporary directory and compares all owned TypeScript files byte for byte with
`src/api`. It checks provenance, the output file inventory, legacy hashes and
unknown files, and exits nonzero when any differs. It does not modify the client.
`generate-api` explicitly updates owned output only after generation succeeds.
It invokes the installed generator's Java JAR directly because its Node wrapper
does not propagate Java failures. The three generated barrel files are removed
according to the existing import convention; three known trailing spaces in
new comment lines are normalized.

## Stable generation and legacy files

The producer's canonical JSON alphabetizes schema properties and removes
`servers`. Those changes alone reordered generated form metadata and changed
the generated fallback URL. After verifying the producer's exact bytes, the
consumer derives a generator-only input: it applies `generator-order.json` to
preserve the existing metadata/property order and uses the historical fallback
`http://localhost:8080/`. The application still uses `environment.basePath`.
The producer spec and its hash are never changed. Unknown fields retain their
producer order. The order-hints file has a recorded SHA-256 in
`src/api/contract-source.json`; any change requires review and regeneration.
Numeric JSON tokens are preserved as written, including integers outside the
JavaScript safe range. The generator revision is fixed by the lockfile.

`legacy-files.json` lists 50 TypeScript files and two historical OpenAPI JSON
files absent from the current generated output. `legacy-hashes.json` freezes
their bytes and the strict check fails on changes or missing entries. Three of
the 50 TypeScript files have reachable imports in the current application:
`apiKnowledgeBlogPart.ts`, `apiProcessDocument.ts` and `apiProductLabelGet.ts`.
A static import traversal starting at `src/app` and `src/shared` found no paths
to the other 47; dynamic imports and external consumers were not excluded.
They are retained as an explicit compatibility inventory, not represented as
generated by the pinned contract. Review their removal or migration separately.
Unexpected TypeScript files outside both inventories cause the check to fail.

## Checking or adopting a backend artifact

For an identified candidate artifact pair:

```bash
npm run check:api -- --spec /path/openapi.json --manifest /path/manifest.json --repository OWNER/inatrace-backend --revision FULL_SHA
```

A different candidate reports drift until its client and provenance are
reviewed and updated. To adopt it, independently verify the producer, place the
pair in this folder, run `npm run generate-api`, inspect the complete diff and
compile and test its consumers. Commit the pair and client together. Failed
generation preserves the existing client. The current policy accepts clean
producer artifacts; dirty working-tree exports are not accepted as release
provenance. Coordinate incompatible changes across backend/frontend deployment;
review mobile consumers separately. Do not edit generated TypeScript manually.

## Initial contract review

The prior `src/api/apidocs-original.json` is OpenAPI 3.0.0 with 179 paths;
the pinned producer artifact is OpenAPI 3.0.1 with 173 paths. Comparing HTTP
method and path yields 12 removed operations (including five `/error` methods,
old currency/evidence list routes, label values and CSV routes) and three added
operations (knowledge-blog delete, onboarding state and authenticated feedback
list). These numbers are an inventory, not proof of endpoint compatibility.

A textual search of the current frontend application and local mobile checkout
found no literal matches for the removed application paths. Mobile uses its own
HTTP implementation, including login/profile, farmer create/list, and plot add
and GeoID routes; it does not use this generated Angular client. That search
cannot exclude constructed routes or changes in payload semantics. No backend
API is changed by this frontend branch, and mobile's compatibility with any
future backend rollout must be tested separately. The mobile checkout contained
uncommitted changes when inspected and was not modified by this work.

The generated GeoJSON upload method uses the `InlineObject2` generated type in
place of `InlineObject`, and its `ByMap` parameter name changes accordingly;
review any external consumers of the generated package before rollout. The
application compiles with the regenerated output and the retained legacy files.

## Model interface audit

`npm run audit:api-models` compares TypeScript interface member declarations
by name and type without considering member order. It reports models with equal
bytes, equal interface declarations, changed declarations and absent output.
The audit also does not compare interface inheritance or type parameters.
Equal members do **not** establish runtime equivalence: generated namespaces,
enums and `formMetadata().vars` are not compared, and metadata order can affect
form control construction. Audit the actual runtime output before alignment.
Before preserving metadata order, 198 changed models had equal interface member
declarations; 44 model files remain absent from generator output. Direct source imports
exist for `apiKnowledgeBlogPart`, `apiProcessDocument` and `apiProductLabelGet`.
